# 多模态文档问答系统 (Multimodal RAG)

支持**含图表 PDF** 的智能问答系统。除了文本内容，还能理解文档中的**表格、示意图、流程图**，并给出带引用溯源的答案。

> 🚀 **在线体验**：https://www.modelscope.cn/studios/aalllllong/multimodal-rag

---

## ✨ 核心设计：两阶段多模态架构

传统 RAG 只能处理纯文本，而真实文档里大量信息藏在**图片和表格**中。本项目采用两阶段设计：

```
【检索阶段】 图片 ──视觉模型──→ 文字描述(caption) ──embedding──→ 向量库
                 (快、便宜、适合语义匹配)

【生成阶段】 命中图片 → 回传【原始图片】给视觉模型 → 生成答案
                 (无损、精确,保留表格中的具体数字)
```

**为什么这样做？**
- 只用 caption 生成：模型看到的是「表格包含学分、外语等级等字段」这种**转述**，具体数字容易丢失
- 回传原图：模型直接读表格中的精确数据，答案准确性显著提升
- 检索用 caption 而非原图：图片 embedding 需要额外模型且中文效果弱，文本 embedding 更成熟可靠

## 🏗️ 系统架构

```
┌─────────────┐   HTTP    ┌──────────────┐        ┌──────────────┐
│  Streamlit  │ ────────→ │   FastAPI    │ ─────→ │  ChromaDB    │
│   前端(7860)│           │   后端(8000) │        │  向量库      │
│  · 问答界面 │ ←──────── │  · /ask      │        └──────────────┘
│  · 检索仪表盘│           │  · /search   │               ↑
└─────────────┘           │  · /images   │        ┌──────────────┐
                          └──────┬───────┘        │  DashScope   │
                                 └───────────────→│ qwen-vl /    │
                                                  │ embedding-v3 │
                                                  └──────────────┘

【离线管线】PDF ─→ 解析(文本+图片) ─→ 图片生成描述 ─→ 向量化入库
【在线管线】提问 ─→ 检索(caption匹配) ─→ 原图+文本 ─→ 视觉模型 ─→ 答案
```

## 🛠️ 技术栈

| 层 | 技术 |
|----|------|
| 文档解析 | PyMuPDF（文本抽取 + 图片导出 + CMYK→RGB 转换 + 小图标过滤） |
| 多模态理解 | Qwen3-VL-Plus（`qwen3-vl-plus`，图片描述生成 / 多模态答案生成） |
| 向量化 | DashScope text-embedding-v3 |
| 向量库 | ChromaDB（持久化 + cosine 相似度） |
| 后端 | FastAPI + Pydantic |
| 前端 | Streamlit（问答 + 检索仪表盘） |
| 部署 | Docker + ModelScope 创空间 |

## 🚀 本地运行

```bash
# 1. 安装依赖
pip install -r requirements.txt

# 2. 配置密钥(.env)
BAILIAN_API_KEY=your_dashscope_key

# 3. 入库(离线跑一次)
python src/ingest.py

# 4. 启动后端
python src/api.py

# 5. 启动前端(另开终端)
streamlit run src/app.py

# 6. (可选)混合检索 + 精排 —— 线上未启用,本地可跑
pip install jieba rank-bm25           # BM25 混合检索必需(已含在 requirements.txt)
pip install sentence-transformers     # 精排必需:含 PyTorch,约 2-3GB,首次再下载 1.1GB 模型
python src/retrieve_hybrid.py         # use_rerank=True 即走 Cross-Encoder 精排
```

> 线上（魔搭创空间）默认走纯向量检索：`api.py → retrieve()`，不依赖 `sentence_transformers`，
> 因此 Docker 镜像保持轻量（`requirements.txt` 共 10 个包）；混合检索与精排作为**本地实验链路**独立存在。

## 🚢 部署（Docker + 魔搭创空间）

- `Dockerfile` 先只拷贝 `requirements.txt` 安装依赖（利用镜像层缓存，改代码不必重装），再拷贝项目代码；`start.sh` 在同一个容器里同时拉起 **FastAPI:8000（仅容器内部）** 与 **Streamlit:7860（对外暴露）**。
- 平台只反代对外端口，所以 `ms.show` 域名访问到的是 Streamlit 页面，FastAPI 的 `/docs`、`/ask` 不对公网开放（Streamlit 作为唯一入口）。
- ⚠️ 创空间是 **prebuild 镜像**模式：`git push` 只更新仓库文件，**不会自动重新构建**。改完代码必须在创空间页面手动重新部署，否则线上跑的还是上一次构建的镜像。

## 📊 检索质量评测（离线可复现）

评测脚本与标注集都在 `eval/`，一条命令跑三档配置并生成 `eval/report.md`：`uv run python eval/run_eval.py`

- **语料**：与线上同一份向量库，14 块（`学位授予细则.pdf` 的 11 个文本块 + 3 张图片描述）
- **标注集**：40 条 = 30 道原词题 + 10 道改述题，正确答案为 chunk id，命中 top-3 即算召回
- **随机基线**：HitRate@3 ≈ 21.4%

| 检索配置 | HitRate@3 | MRR@3 | Top1 命中 | 40 题耗时 |
|---|---|---|---|---|
| 纯向量 | 97.5% | 0.917 | 87.5% | 7.0s |
| 混合（BM25 + RRF） | **100.0%** | 0.921 | 85.0% | 7.7s |
| 混合 + 精排（Cross-Encoder） | 97.5% | **0.933** | **90.0%** | 174.6s |

按题型拆开看，结论比整体数字更有价值：

| 检索配置 | 原词题 Top1 | 原词题 MRR | 改述题 Top1 | 改述题 MRR |
|---|---|---|---|---|
| 纯向量 | 86.7% | 0.922 | **90.0%** | **0.900** |
| 混合（BM25 + RRF） | 86.7% | 0.933 | 80.0% | 0.883 |
| 混合 + 精排 | **93.3%** | **0.967** | 80.0% | 0.833 |

**怎么读这组数**：HitRate@3 三档都接近饱和（97.5%–100%），区分度要看 MRR 与 Top1。精排更像"字面重合放大器"——原词题 Top1 从 86.7% 提到 93.3%（MRR 0.967），但改述题反而降到 80%，同时单量约 4.4s/题（纯 CPU）、镜像增重约 2GB、首次还要下载 1.1GB 模型，因此**线上默认纯向量**，混合与精排保留为本地实验链路。

## 🔬 附带实验：单阈值拒答能做到什么程度

用 40 条正样本 + 5 条负样本测过 top-1 相似度分布：

- 正样本 top-1 相似度：min 0.5415 / 中位 0.7033 / max 0.8136
- 负样本：食堂 0.4713、宿舍 0.4933、奖学金 0.5442、硕士答辩 0.6303、**博士学位条件 0.7083**

| 阈值 | 挡住的负样本 | 误拒正样本 |
|---|---|---|
| 0.50 | 2 / 5 | 0 / 40 |
| **0.55** | 3 / 5 | 1 / 40（2.5%） |
| 0.60 | 3 / 5 | 5 / 40 |

**结论**：单一分数阈值只能挡住"完全跑题"的问题；**同域但库里没有答案**的情况（问博士条件、库里只有本科细则，相似度 0.7083 反而高于多数正样本）挡不住，需要额外的 answerability 判定（把候选片段与问题一起交给模型判断"能否回答"）。另外，门控必须挂在向量分数上——混合模式的 RRF 分数上界只有约 `2/(60+0+1) ≈ 0.033`，不能当相似度阈值使用。

## 🧗 工程踩坑记录（都用脚本量化过）

| 问题 | 症状 | 处理 |
|---|---|---|
| 图片描述缓存整份重写 | 每新增一张图就把全部条目重新序列化写盘：200 张图实测**最终文件 87KB，累计写入 8.77MB（放大 100.2 倍）**；且写入非原子，中断会留下半个 JSON，而读取端当时没有异常保护 → 整份缓存直接报废 | 给出两套改造：JSONL 逐行追加（写入量 O(N)、坏行跳过）或"临时文件 + `os.replace` 原子替换 + 每 N 张落盘"（保持 JSON 格式）；读取补 `try/except` |
| 向量库混入外部污染数据 | 库里 142 块中有 **128 块**来自一份已不在项目里的复习手册（占 90%），提问会召回讲代码的段落 | 删除并重建向量库（142 → 14 块），`source` 元数据修正为真实文件名 |
| 精排分数没有写回 | 精排只调整了顺序，分数仍是融合分，前端显示的"精排分"与排名对不上 | 修正为把 `float(score)` 写回候选并重新排序，并补一条测试用例守住 |
| 空库除零 | 库里没有文档时 `BM25Okapi([])` 抛 `ZeroDivisionError`，接口直接裸 500 | 检索前判空返回 `[]`；接口层把异常统一转成结构化 JSON（500 / 503 带 `detail`） |

## ⚠️ 已知限制

- 图片描述质量依赖视觉模型能力，复杂图表可能描述不完整
- 当前单文档场景验证，尚未测试大规模文档集
- 检索层的现状是**主动取舍**，不是没做：混合检索（BM25 + RRF 融合）与 Cross-Encoder 精排均已实现于 `src/retrieve_hybrid.py`，但只作本地实验链路，**线上默认纯向量**。原因是成本：`sentence-transformers` 带 PyTorch，镜像体积 +约 2GB、冷启动显著变慢，精排模型（`BAAI/bge-reranker-base`）首次运行还要再下载 1.1GB；而本项目是**单文档 14 个片段**的小库小流量场景，收益不足以覆盖这笔启动成本。三档检索质量的实测对照见上文「📊 检索质量评测」。
